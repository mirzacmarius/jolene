# The workshop's team signs in with Google too

The team signs in to the workshop as couples sign in to their accounts, with a code emailed to an address on `WORKSHOP_EMAILS` (docs/adr/0009). Marius asked on 2026-10-24 for Google sign-in for the team, so that a team member opens the workshop with the Google account they're already signed in to, rather than waiting for a code and typing it each time. The code stays, for couples and for the team.

- **Convex Auth's Google provider, for the workshop's addresses only.** `convex/auth.ts` adds Auth.js's Google provider beside the email and anonymous ones. It asks Google for the address alone (`openid email`), and shows Google's account chooser each time, so a browser signed in to several Google accounts picks the right one. A Google account signs in only when Google has verified its address and the address is on `WORKSHOP_EMAILS` (`workshopGoogleProfile`). Anyone else comes back to the studio signed out: couples sign in with a code as before, and the studio keeps no one's Google profile.
- **The same account as the code's.** The account keeps the address and nothing else of Google's, and Convex Auth gives a Google sign-in the account that already has the same verified address. A team member who signed in with a code before finds the same account. Taking an address off the list shuts it out of the workshop whichever way it signs in.
- **Only the workshop offers it.** The workshop's sign-in shows "Continue with Google" above the email form once the deployment has Google's client (`accounts.me` says `googleSignIn`). The account page offers the code alone.
- **Back to the page it started from.** Google sends the browser back to Convex's own address, `https://<deployment>.convex.site/api/auth/callback/google`, the one redirect URI Google's client lists, and Convex sends it on with a code to the studio's page the sign-in started from. Convex Auth's `redirect` callback (`studioPage`) allows only the studio's pages at `SITE_URL`, or at `/studio` on the shop's address (`SHOP_URL`) where production serves the studio (docs/adr/0004), so no other site can be handed the code. A sign-in that comes back without one, refused or cancelled at Google, says so on the form.
- **Designs move with it.** The studio trades the code for the account's session itself (`SignInReturnProvider`), once the browser's own session has loaded, where Convex Auth's provider would trade it before. The request then carries the anonymous session, and what the visitor made anonymously moves to the account as it does with a code (docs/adr/0011, docs/adr/0009). It waits until no refresh of that session's token is under way, behind the lock Convex Auth's provider takes to refresh one: the trade ends the anonymous session, so a refresh still in flight would come back empty and sign the visitor out again.

## Consequences

- Marius makes the OAuth client in Google Cloud (Google Auth Platform, Clients: a Web application) with production's redirect URI, `https://quaint-ibis-260.convex.site/api/auth/callback/google`, and sets its `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET` on Convex production. Until both are set the workshop offers the code alone. The app asks only for the address, which Google lets an app ask for without reviewing it first.
- Google's screens name the address it sends the browser back to, `quaint-ibis-260.convex.site`, as the site being signed in to, until Convex serves the deployment on a domain of Jolene's.
- Moving to jolene.ro changes nothing at Google, since the redirect URI is Convex's: the studio's new address comes from `SHOP_URL` and `SITE_URL`, set at the switch.
- Each listed address is a Google account's own: a team member whose Google account has another address adds that one to the list.
- The variables go on production only: the client lists no preview's Convex address, so previews go on signing in with a code.
